# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

School registrar document portal for two institutions (**ISAP** and **MCNP**). Students register, verify by email OTP, get approved by a registrar, and then upload required documents (PSA certificates, Form 137, Good Moral, etc.). Registrars review submissions. A system admin manages accounts, courses, audit logs, and DB backup/restore.

Plain procedural PHP. There is no framework, router, build step, test suite, or linter. Every `.php` file in the root is a page or an endpoint that you reach directly by URL.

## Running locally

- Stack: XAMPP on Windows (PHP 8.2, MariaDB/MySQL). The app is served from `C:\xampp\htdocs\REGISTRAR`, so the URL is `http://localhost/REGISTRAR/`.
- Database name: **`registrar`** (credentials are in `config.php`; the default is `root` with no password).
- PHP binary: `C:\xampp\php\php.exe`. MySQL CLI: `C:\xampp\mysql\bin\mysql.exe -u root registrar`.
- Dependencies: `composer install` (PHPMailer, setasign/fpdf, setasign/fpdi). `vendor/` is present.
- Syntax-check a file: `C:\xampp\php\php.exe -l <file>.php`.
- Preview the notification email template in a browser: `email_preview.php?type=success|warning|info&subject=...`.
- The first request that loads `db.php` auto-creates the system admin account. Log in with the email `Admin` (case-sensitive) and the password `adminmcnp-isap`.

There is no schema/migration file. The schema lives only in the live DB. Inspect it with `mysql -e "DESCRIBE <table>"`, or with the throwaway scripts `scratch.php`, `show_tables.php`, `show_cols.php`, and `check*.php`.

## Architecture

### Request pattern
- **Pages** (`*_dashboard.php`, `submissions.php`, `checklist.php`, etc.) are large, self-contained files. Each one does `session_start()` → `require_once 'db.php'` → role check → queries at the top, then renders full HTML with its own inline `<style>` and `<script>`. There are no shared layout/header/sidebar includes: every page repeats the sidebar markup and CSS. A UI change that should look the same everywhere has to be made in every page for that role. `patch.py` shows the search-and-replace approach used for this in the past. `style.css` and `register.js` are not referenced by any page.
- **Shared mobile CSS:** there are two shared stylesheets, each linked after the page's inline styles:
  - `student_mobile.css` — the seven student-only pages: `student_dashboard`, `my_document`, `student_calendar`, `student_notifications`, `checklist`, `student_request` and `student_settings`.
  - `registrar_mobile.css` — the eleven registrar pages: `registrar_dashboard`, `analytics`, `calendar`, `submissions`, `reject`, `registrar_requests`, `notifications`, `archive`, `typesofdocuments`, `users_approved` and `registrar_settings`.
  - Both show a fixed top bar at ≤1024px, `<header class="mobile-appbar">`, that holds the `.mobile-toggle` menu button, and give `body` top padding for it. New pages should use the same header markup instead of a floating button.
  - `submissions.php` and `reject.php` are shared with students (`body.student-mode`). Both now render the same app bar for students as for registrars ("Student Portal" / the role), and link `student_mobile.css` for a student; their `body.student-mode` phone block drops the old floating-button room (`padding-left: 65px`) and the second `.mobile-topbar-logo`, so the title sits at the left edge like every other student page. So every structural rule in `registrar_mobile.css` is scoped to `body:not(.student-mode)`, which also gives it the specificity to override each page's own `@media (max-width: 1024px)` block — notably the `padding-left: 65px` topbar hack that reserved room for the floating button, and the cramped 4-across `.stat-cards` grid.
  - `registrar_mobile.css` also supplies the `.sidebar-overlay` defaults for `reject.php`, which has no overlay rules of its own.
- **Handlers** (`process_*.php`, `save_event.php`, `send_doc_reminder.php`) accept POST, check `$_SESSION['role']`, write to the DB, set `$_SESSION['flash']` (sometimes also `flash_type`), and `header("Location: ...")` back to a page. `send_doc_reminder.php`, `fetch_*.php`, and `mark_notification_read.php?ajax=1` return JSON for `fetch()` calls.
- **Table search boxes** all go through `search_helper.js` (`SearchKit`). It is loaded in `<head>` by `submissions`, `reject`, `users_approved`, `archive`, `analytics` and both dashboards. Every query word must appear in the row, in any order; case, accents and punctuation are ignored, and IDs match with or without the dash. Buttons and form controls (and `[data-search-ignore]`) are never searched, and a row may supply `data-search`. It listens on `input` (Esc clears), shows a `3 / 12` count in the box and a "No results" row. A page keeps its own dropdown filters and passes them as the `extra` predicate to `SearchKit.filterTables()`. The dashboards re-run it through `window.runDashboardSearch` when the section changes. Keep the file ASCII-only in code, because Apache serves `.js` without a charset. `registrar_requests.php` and the admin Audit Trail search on the server instead.
- Front-end libraries are loaded from CDNs per page: Font Awesome, Inter font, FullCalendar 6, and Chart.js. PDF.js 3.11 (cdnjs) is lazy-loaded by the document viewer (`doc_viewer.js`).

### Auth, roles, and account state
- Session keys: `user_id`, `email`, `role`. Roles in use: `student`, `registrar`, `systemadmin`. The enum also has an unused `admin`.
- `users.is_verified` is a state machine, not a boolean:
  - `0` = email not verified (OTP pending)
  - `1` = OTP verified, awaiting registrar approval (students can't log in)
  - `2` = approved/active
  - `3` = rejected
- `process_login.php` enforces these states and redirects by role to `admin_dashboard.php`, `registrar_dashboard.php`, or `student_dashboard.php`. `admin_dashboard.php` also requires `$_SESSION['email'] === 'Admin'`.
- OTPs (registration, resend, and password reset) are stored as `password_hash` in `users.otp_hash`, with `otp_expires` (a unix int, 10 minutes) and `otp_attempts` (max 5). The password reset flow is `forgot_password.php` → `verify_reset_otp.php` → `reset_password.php`, carried in `$_SESSION['reset_email']` and `can_reset_password`.
- `is_archived` soft-hides users. Registrars archive students (`process_student_status.php`); the admin archives any user (`process_user_action.php`). The default `Admin` account cannot be modified.

### Naming and student lists
`name_helper.php` is the single formatter for people's names. `formatPersonName($first, $middle, $last)` (and `formatPersonNameRow($row)`, which reads `first_name`/`middle_name`/`last_name`) returns **"Last, First M."**, and `formatStudentId()` renders a blank student number as an em dash. Every table that lists students puts the **Student ID column first**, then the name, and sorts by `last_name`. This covers `analytics.php`, `submissions.php`, `reject.php`, `registrar_dashboard.php`, `users_approved.php`, `archive.php`, `admin_dashboard.php` (Users, Archived and the JS-rendered program students), the audit trail (`fetch_audit_logs.php`, including the CSV), `notifications.php`, `send_doc_reminder.php` and the `download_merged_pdf.php` cover and file name. A page's own greeting and avatar initials keep the natural first-name order, as do registrar names inside sentences.

### Student profile
- `profile_config.php` is the single source of truth: the sections and fields (`getProfileSections()`), the schools a student lists from earliest to latest (`getProfileEducationLevels()`), validation (`validateStudentProfile()`) and `ensureProfileColumn()`. Adding a field means adding it there and nowhere else.
- Everything beyond the existing `users` columns is JSON in **`users.profile_data`** (birth date, sex, civil status, parents, guardian, `education.<level>.{school,address,year_from,year_to,extra}`), so a new field needs no schema change. **Age is never stored** — `profileAge()` works it out from the birth date.
- The student edits it only in `student_settings.php` (Edit Profile, `#edit-profile`), which draws its inputs from the config. `process_profile.php` saves nothing while any answer is invalid: it stashes what was typed in `$_SESSION['profile_old']` and the reasons in `$_SESSION['profile_errors']`, and the form comes back as the student left it. Name, student ID and e-mail are read-only there.
- **Every address in the profile is picked, never typed** — the permanent address (`home`, with ZIP), the guardian's (`guardian_place`) and each school's. A field of type `address` is stored as an array of `region` / `province` / `city` / `barangay` (+ `street`, `zip`); `$place_picker` in `student_settings.php` renders the four `<select data-place>` inside a `[data-place-group]`, and `address_picker.js` links each group and fills it from the local files in `psgc/` (`regions.json`, then one `p_<4-digit province code>.json` per province with its cities and barangays: 17 regions, 1,634 cities/municipalities, 42,029 barangays, built from the public PSGC lists; a "province" is the first four digits of the code, which files independent cities under their geographic province, and Metro Manila's are its districts). `psgcCheckPlace()` in `psgc_helper.php` checks a posted chain against the same files, accepting a partial chain when saving. `profileComposePlace()` joins one into a line: `process_profile.php` writes the completed permanent address into `users.address` (which the request forms print) and leaves an older typed address alone until one is picked, and each school row keeps its joined `address` for `prev_school_address`. **A school is picked from the place's own schools:** each education level asks for the school's address first; once its city is chosen, `school_picker.js` fills *Name of School* from `psgc/s_<province code>.json` — 60,809 schools from the DepEd masterlist of schools SY 2020-2021, each placed in a PSGC city by name (aliases in the build script cover DepEd spellings and Manila's districts) and tagged with its levels (1 elementary, 2 JHS, 4 SHS, matching the level's `school_list`) — the chosen barangay's schools first. *My school is not on the list* reveals the text input that is the real `[school]` field; colleges are not in the list and keep a plain text box. `address_picker.js` announces every city / barangay change with a `placechange` event for this. Father and mother are separate sections (`father`, `mother`), each with its own name split into last / given / middle and its own `*_place` address; every address field with `copy_home` gets a *Same as my permanent address* button (`data-copy-from` / `data-copy-to`, which calls the target group's `setPlace()`). A section's `missing_prefix` ("Father's ", "Guardian: ") makes its short labels unambiguous in the missing-details list; a value typed before the split (`father_name`, `mother_name`, `guardian_address`) is still shown as a hint until the student re-enters it.
- **"Incomplete" has one definition: `profileMissingFields($user, $profile)`**, the labels of the `required` fields (plus contact number, home address and the school of every `always` level) that are still blank. `required` never blocks a save. There is no "complete" notice in Edit Profile: `process_profile.php` sets `$_SESSION['profile_completed']` only on the save that takes the list from non-empty to empty, and Settings then shows a one-time *Your profile is complete!* modal (`#pfDone`). That list drives the red count on the student's sidebar picture and the red dot on the phone menu button (`student_profile.js`, from `student_profile_view.php?status=1` or `<body data-profile-missing>`, remembered in `sessionStorage`), the notice and red asterisks in Edit Profile, and the footer of the profile modal for both student and registrar.
- **Clicking the sidebar picture opens the profile read-only.** `student_profile.js` + `student_profile.css` inject the modal (the `doc_viewer.js` pattern), make the first child of `.sidebar .student-info` a button, and also open from any `[data-open-profile]`. The content is the fragment `student_profile_view.php` (own profile only), fetched once per page view and prefetched on hover/touch. All nine pages a student sees link the two files; `submissions.php` and `reject.php` only inside `if ($role === 'student')`. A registrar opens a student's profile through the same modal: any element with `data-profile-id="<user id>"` (the student name in `analytics.php`, a `span.sp-link`, not a button, so `SearchKit` still searches it) fetches `student_profile_view.php?id=N`, which serves only students of the registrar's own institution and ignores `id` for a student. On registrar pages the modal takes the dark palette from `html[data-theme-base="dark"]`.

### Light mode / dark mode
- `theme_mode.js` + `theme_mode.css` replace the old Theme Personalization cards. Every student and registrar page loads the script right after the viewport meta, **not deferred**, so the mode is on `<html>` before the first paint. `data-base` is the mode the page's CSS is written in (student pages `light`, registrar pages `dark`), `data-key` the localStorage key (`student-theme` / `registrar-theme`), and `data-clear` deletes the old colour keys, so the colour loaders still at the bottom of each page are now no-ops. `submissions.php` and `reject.php` pick the tag by role.
- The other mode is **not a second palette**: `html[data-theme-invert]` inverts the whole page and rotates the hues back, so every hard-coded colour keeps its designed contrast. Real pictures and paper are flipped back (`img`, `video`, `iframe`, the document viewer's canvases, `.rf-page`), and modal veils are overridden so they still dim. Add anything new that shows a photo or a real sheet to that list in `theme_mode.css`. **Student dark mode is tuned to the registrar's palette** (page `#0f172a`, cards `#1e293b`, gold accent): the block between `STUDENT-DARK-START` and `STUDENT-DARK-END` sets `--primary-color` / `--bg-color` / `--sidebar-bg` and repaints every rule that had a white or near-white background, each with the colour the inversion turns *into* the wanted one (the table in that block's comment). A new white surface on a student page that is not in those selector lists still works but shows black instead of navy, so add its selector there.
- `theme_mode.js` adds the switch itself: a round `.theme-fab` button at the top right of every themed page (moon in light mode, sun in dark), so no page carries markup for it. `placeButtons()` appends it to the page's `.topbar` / `.top-bar` (inside the existing right-hand group when there is one, because the bars are `space-between`), floats it in `.main-content` on the pages with no top bar, and puts a second copy in `.mobile-appbar` that takes over at 1024px and below. Any `[data-theme-choice="light|dark"]` control switches too; the Appearance card sits in `student_settings.php` and `registrar_settings.php`. Bump `theme_mode.*`'s `?v=` in all 18 pages when changing them. `admin_dashboard.php` is not themed.

### Institution scoping
`users.institution` (`ISAP` / `MCNP`) partitions data. Registrar pages filter students and documents with `u.institution = ?` using the logged-in registrar's institution, and fall back to unfiltered queries when it's empty. Keep this filter when you add registrar queries. `analytics.php` also takes `?course=` and `?year=`, which narrow **every** query on the page — cards, all three charts and the compliance table — through one `$filter_sql` joined on `users u`. Its options come from `programs.php` plus any stored value, and each count is faceted (a course counts what it gives with the chosen year, and the other way round). An unknown value falls back to all. The name/ID search is client-side, and *Notify All Incomplete* only reaches the rows on screen. The course/department lists per institution are hardcoded in JS in `index.php` (the registration form) and stored in `users.course`.

### Document pipeline
1. `checklist.php` lists `document_types`. Its JS checks file type and the 10 MB limit (`DOC_MAX_UPLOAD_BYTES`, in `upload_config.php`) instantly in the browser. There is no OCR and no document-type validation.
   - **View** opens the `DocViewer` modal from `doc_viewer.js` and `doc_viewer.css`, which `my_document.php`, `submissions.php` and `reject.php` also use — the two registrar pages used to carry their own `openPreview()` and a `#preview-panel` modal whose close button was pushed off the panel by a long document name on a phone; that copy is gone, and the shared viewer's `openPreview(path, title)` keeps every call site unchanged. The JS injects its own modal markup, so a page only needs to link both files and call `openPreview(path, title)`.
   - Images and PDFs share one zoom model: zoom 1 fits the screen, the content is resized, and the stage scrolls.
   - PDFs are drawn to canvases with PDF.js and re-rendered sharper when zoomed. Files PDF.js can't read fall back to an iframe.
   - Zoom controls: the toolbar buttons, `+`/`-`/`0`, pinch, double-tap, and wheel (Ctrl+wheel for PDFs).
   - File paths are passed through `data-file` attributes, never interpolated into inline JS.
   - Each row shows the latest upload for that type, including rejected ones, with the registrar's note underneath so the student can re-upload a corrected copy.
2. `process_checklist_upload.php` enforces the same limits on the server. It saves the file to `uploads/<time>_<name>` and inserts it into `documents` as `pending`. **Nothing is decided automatically.** The student gets an `info` notification that the document is waiting for review.
3. A registrar decides every document with `process_document_status.php` (`approved`/`rejected`). It is the only place a document leaves `pending`:
   - A rejection **must** carry a note of at least `DOC_MIN_FEEDBACK_LENGTH` characters (`upload_config.php`); the handler refuses an empty one. That note is stored in `documents.feedback`, sent to the student as a `warning` notification and email, and shown on their checklist, `my_document.php` and `submissions.php`.
   - An approval note is optional, and approving clears any earlier rejection note.
   - `documents.reviewed_by` / `reviewed_at` record who decided and when, and the registrar pages show it.
   - The handler scopes by institution: a registrar can only decide documents belonging to students of their own `users.institution`.
4. `submissions.php` lists everything except rejected and `reject.php` lists the rejected ones. For a registrar, `submissions.php` shows **one row per student** (students with pending files first, then latest upload). Clicking the row opens that student's files underneath (`tr.stu-docs` → `.doc-item`), and which students are open survives the post-decision reload via `sessionStorage`. Search and the document-type filter work per file, so a student is listed when one of their files matches, and a narrowed group opens on its own. `reject.php` uses the same grouped layout for a registrar (`RejGroups`, open groups kept under `registrar-open-rejected`), without the checkboxes; its phone rules need `!important` because that page's generic phone table rules are all `!important`. Download As One sends only the ticked files that are shown. Students still get the flat table. The sidebar's Submissions entry comes from `submissionsNavLink()` in `request_config.php`, with a red count of pending documents, the same pattern as `requestsNavLink()`. Both pages let a registrar accept a document or rewrite the note. The Status column holds only the badge (`Pending` / `Approved` / `Rejected`) — the note is never printed in the table. A **Rejected** badge is a button that opens the shared note modal (`#noteModal`, `openNoteModal()`), which reads the note, document, student and reviewer from `data-*` attributes on the badge. Both pages carry their own copy of that modal's markup, CSS and script, as the project has no includes. The student's checklist still shows its rejection note inline, because that is where they act on it. `download_merged_pdf.php` uses FPDI to merge the selected documents behind a generated cover page. The registrar dashboard's **Recent Submissions** card has a tab per status (`.recent-tab`: Recent / Pending / Approved / Rejected). It loads the five newest files overall *and* the five newest of each status, each row marked `data-status` and `data-recent`, so a tab is never empty just because newer uploads pushed its rows out; the number on a tab is that status's real total. The tab is passed to `SearchKit.filterTables()` as the `extra` predicate, so it combines with the dashboard search, and View All points at `reject.php` on the Rejected tab.

**Every upload is also kept in the database** (`upload_store_helper.php`), because the project gets moved between computers and a DB backup/restore used to arrive without the files. Each upload handler (`process_checklist_upload.php`, `process_upload.php`, `process_profile.php`) calls `storeUploadInDb()` after saving to disk, and `process_delete_document.php` calls `deleteStoredUpload()`. The bytes live in `upload_files` + `upload_file_chunks` in 512 KB chunks (the server's `max_allowed_packet` is 1 MB). Both tables are **Aria, not InnoDB**, because creating a new InnoDB table crashed this XAMPP's mysqld. Their paths are `VARCHAR(191)`, since Aria keys are capped at 1000 bytes.
- `uploads/.htaccess` rewrites any request for a missing file to `uploads/_restore.php`, which writes the file back from the DB (`ensureUploadOnDisk()`) and serves it. So pages keep linking `uploads/...` directly. Code that reads an upload from disk must call `ensureUploadOnDisk()` first, as `download_merged_pdf.php` does.
- The same `.htaccess` blocks every other `.php` in `uploads/` and marks uploads cacheable for a year, because names are timestamped and never reused.
- New files are saved as `<time>_<safeUploadFileName()>`: ASCII only, safe in a URL. `documents.file_name` keeps the original name for display.
- `checklist.php` shrinks JPEG/PNG photos over 1.5 MB or wider than 2200px to a JPEG in the browser before sending, and keeps the original whenever that doesn't make the file smaller.

`auto_verify.php` held the old GD blur-detection auto-approval. It is no longer referenced by any page and is kept only for reference; the upload limits it used to define now live in `upload_config.php`.

`process_upload.php` / `my_document.php` is an older upload path with no document type.

### Request pipeline (registrar forms filed online)
Separate from document uploads. A student files a registrar form, the registrar approves it and sets **when it may be claimed**, and the pick-up is recorded.

- `request_config.php` is the single source of truth and the only file to touch when adding a form. It creates `student_requests` idempotently (the same "create if missing" pattern as `audit_log_helper.php`), defines the form as sections of fields, the requirement and declaration checklists, the status presentation (`requestStatusMeta()`), and `requestsNavLink()` — the sidebar entry each registrar page echoes, badge included, since the project has no includes.
- **Institution gating** lives in `getRequestFormsForInstitution()`. `ISAP` offers four request types: **Application for Graduation** (`Form No. 005`, `graduation`), **Request for Form 137-A** (`form137`), **Request for Transcript of Records (OTR)** (`otr`) and **Request for NSTP Serial Number** (`nstp`, which has no QMS number and cites CHED CMO No. 27, s. 2015). **`MCNP` offers the Application for Graduation, Form 137-A, OTR and NSTP Serial Number** on its own letterhead (its NSTP letter shares `$nstp_form` with ISAP and is printed on the Form 007RF137 sheet, title and document box included, because that is what the paper says); its other forms go in the same array as their paper versions are finalised. Adding a form means: an entry in that array and a `case` in `getRequestFormSections()` — plus a renderer branch only if it is not a letter.
- **The graduation sheet is shared between the institutions.** `$graduation_form` describes it once and each institution supplies only its `code` and `letterhead`, so the checklist, waiver and signatories can never drift apart. A letterhead carries the school's `name`, `website`, `email`, `doc_no`, plus the **`color`** its name is printed in (ISAP red `#c00000`, MCNP blue `#1f4e9c`) and the **`logo`** beside it. The HTML sets the colour inline and the PDF converts it with `RequestFormPdf::rgb()`.
  - Each letterhead uses its own seal: **`logo_isap.png`** and **`logo_mcnp.png`**, 320×320 RGBA PNGs trimmed square from the supplied artwork (FPDF 1.82 embeds the alpha as an SMask, so the PDF keeps the transparency). `download_request_form.php` falls back to `logo.jpg` if a named file is missing.
  - `logo.jpg` / `logo.png` / `isaplogo.*` are all the **combined** MCNP+ISAP seal and are still what every page's sidebar, app bar and the emails use — only the printed forms switched to the per-institution files.
  - To regenerate from new artwork: trim to the non-transparent, non-white bounding box, pad to square, resample to 320px, save as 8-bit RGBA. A **palette** PNG must go through `imagepalettetotruecolor()` first — otherwise `imagecolorat()` returns palette indexes, which read as solid black and defeat the trim.
- **`form137` and `otr` are two request types on one sheet.** The registrar keeps the Form 007 template under both names (F.137 and OTR) and the printed page is identical, so they share `$form007` — body, table, tick boxes, Ctrl No., signatory — and `getForm007Sections()`, overriding only `title`, `short`, `icon` and `description` (`$form137_request` / `$otr_request`). Each institution wraps it with its own `code` and letterhead: `$isap_form007` (Form No. 007) and `$mcnp_form007` (Form No. 007RF137, with its own table widths and `title_below`). MCNP keeps two copies of the template: the F.137 copy underlines only "Form 137-A" in the body, while the OTR copy underlines the whole document name, so MCNP's `otr` entry overrides `body`. **`title_below`** moves the title onto its own line under the document-control box, centred on the page, with the office line right-aligned beside the box; the HTML takes that line back out of the gaps above the date, tick boxes and stub, so the page stays one A4 sheet. A letterhead's optional **`email2`** prints a second address right-aligned under the first (MCNP's `registrar@`); it adds a line to the letterhead in both the HTML and the PDF, and the HTML letter takes that height back above the date so the sheet stays one A4 page. A form's **`sheet_title`** is what gets printed at the top; it is deliberately separate from `title`, which is only how the portal labels the request. Both print `REQUEST FOR FORM 137-A / TRANSCRIPT OF RECORDS`, because that is what the paper says.
- **A field's `autofill` key says what pre-fills it.** `requestAutofillData($user, $profile, $form_type)` builds the values per form: the `users` columns (`course`, `address`, `full_name`...) plus the Student Profile ([[student profile]] in `users.profile_data`) as `birth_date`, `sex`, `civil_status`, `edu_<level>_school` / `edu_<level>_year`, and `prev_school_name` / `prev_school_address` / `prev_strand_course` / `prev_school_year` — the school the letter is written to, which is the senior high for `form137` and the previous college for `otr` and `nstp`. `prefillValue()` prefers that over the student's previous answers and the field gets the `auto` tag. To pre-fill a new field, give it an `autofill` key that function provides.
- Field definitions are reached through **`getRequestFormSections($form_type)`**, never by naming a form's own function. Field types are `text | date | tel | email | textarea | select | year | checkbox`; a `checkbox` is stored as true/false and is never required.
- Each form supplies its own `confirmation` text — the one thing the student must tick before submitting. It is stored as `form_data.waiver_text`.
- `student_requests.form_data` stores the filled answers as JSON, so a new form does not need a schema change. The columns are only what the registrar filters, sorts or schedules on.
- **Statuses:** `pending` → `approved` (with `claim_at`, `claim_location`) → `claimed` (with `claimed_at`, `claimed_by_name`, `released_by`); plus `rejected` (note required, `REQUEST_MIN_NOTE_LENGTH`) and `cancelled` (student's own, only while pending). A student may have only one open (`pending`/`approved`) request per form at a time.
- `student_request.php` opens with a compact **My requests** card — one line per open request carrying its reference, filed date, status and claim schedule. Each line unfolds that request's four-step tracker and claim slip, which start `hidden`, so two open requests no longer make a wall of cards (a `@media print` rule un-hides them so Ctrl+P still works). Below it sits a picker of the forms the student can still file, one panel per form, pre-filled from `users` and falling back to that form's previous answers. A student may hold one open request per form.
- The request history carries a `.form-filter` chip bar, shown only when there is more than one form to narrow (the picker used to have one too; it was removed as unnecessary for four cards). The JS handler serves any such bar: it scopes to the bar's enclosing `.card` and toggles `hidden` on that card's `[data-form]` elements, so adding a filter elsewhere only needs the same markup. `.req-table tr[hidden] { display: none }` is required, because a `<tr>`'s UA `display: table-row` otherwise beats the `hidden` attribute.
- **A student's filed form is view-only; the only thing they download is the claim slip.** The tracker's actions are **View my form** (`request_form_view.php`, in the viewer) and, once the request is approved, **Download claim slip** (`download_claim_slip.php`). That is enforced everywhere, not just hidden: `student_request.php` passes `allowPrint: false, allowDownload: false` to `openRequestForm()`, the standalone page drops its Print/Download buttons for a student, and `download_request_form.php` — the full filled sheet — now refuses the `student` role outright. The receipt shown straight after filing has no download, because there is no schedule yet.
- `download_claim_slip.php` is the slip as a one-page **A5** PDF (`ClaimSlipPdf`, its own small FPDF class — the form's `RequestFormPdf` lives inside `download_request_form.php`, which runs on include, so it cannot be reused). It is served only for `approved`/`claimed` requests that have a `claim_at`, and only to the owning student or a registrar of that student's institution. It carries the institution's letterhead strip and seal, the reference, claimant, schedule and a ruled *Received by / Released by* block for the counter, using the same convention as the forms: pre-printed captions in black, answers in ink blue on a rule.
- A successful submit does **not** set a flash. `process_student_request.php` sets `$_SESSION['request_submitted']` (id + form type) and the page looks that row up to show a **receipt modal** — reference, filed time, status badge, Download PDF, and a *View my request* button that unfolds that request's tracker on close. The session key is unset on read, so a refresh never re-opens it, and if the row cannot be read back the page falls back to a flash line rather than confirming nothing. Cancels and every error still use the ordinary flash. `process_student_request.php` handles submit and cancel, validating against the same field definitions the page rendered from.
- `registrar_requests.php` is the registrar queue: stat cards, **status tabs, a form-type filter and search**, plus a modal that prints the whole filled form.
  - The three filters combine. `$filter_link()` builds every tab, chip and Clear link so changing one never drops the others, and the modals' `redirect_to` carries them too, so a decision lands back on the same view. `form` may be omitted from a URL (it defaults to all) but `status=all` must stay in it, because a missing `status` means `pending`.
  - The counts are faceted from one grouped query scoped by institution and search: **status tabs count what the chosen form would give, form chips count what the chosen status would give**, so each number is what clicking it produces. That query runs *before* the rows are fetched, so an unknown `?form=` is corrected to `all` first rather than returning an empty page.
  - The chips list the institution's forms plus any `form_type` still present in the table, so a form removed from the config never hides its old rows. Chip labels come from the form's `short` key (`requestFormLabel()`). `process_request_status.php` is the **only** place a request leaves `pending` (`approve`, `reschedule`, `reject`, `claim`), and it scopes by `users.institution` exactly like `process_document_status.php`.
- Every transition notifies the student through `sendNotificationAndEmail()` and writes `REQUEST_SUBMITTED` / `REQUEST_APPROVED` / `REQUEST_RESCHEDULED` / `REQUEST_REJECTED` / `REQUEST_CLAIMED` / `REQUEST_CANCELLED` to the audit trail, always with the student as `target_user_id`.

**The filed form as a document.** A request is not shown as a list of fields anywhere the registrar acts on it — it is drawn as the paper form it replaces:
- `renderRequestFormDocument()` dispatches on `form_type`. The **letters** (`form137`, `nstp`) share one renderer, `renderLetterDocument()`, and one PDF builder, `buildLetterSheet()`, because they share a skeleton: letterhead, date, `THE REGISTRAR` plus three ruled lines, salutation, a pre-printed body, a one-row table, closing and signatory. The config drives the differences — `table` gives the columns and their widths, `options` and `ctrl_no` add the tick boxes and Ctrl No. box that only Form 137 prints, and a `letterhead` **without `doc_no`** leaves the document-control box off the sheet and centres the titles (`.rf-titles.is-wide`). The body's `{b}` `{i}` `{u}` markers survive escaping and become tags in HTML, and font switches in the PDF via `writeRich()`.
- **Graduation** builds the two-page sheet (letterhead, document-control box, the numbered DOCUMENTS table with the student's ticks in the REMARKS column, the waiver and the pre-printed signature blocks), plus a "FOR THE REGISTRAR'S OFFICE" stub the paper form never had, carrying the reference number and the claim schedule. Everything user-supplied goes through `rfEsc()`, because the fragment is injected with `innerHTML`.
- **The letterhead is measured off the printed original**, not eyeballed. Its rule is 894px wide there, so every figure is a share of that width: the seal is **10.5%** of it, **3.2%** in from the left end and **1.2%** below the top rule; rule-to-rule is **14.4%**; the four lines are ~12pt with a 24.5px pitch and are **centred on the whole width**, not on the space beside the seal — that is what puts the seal right up against the name (about 12mm clear of it, as on the paper). Colours are sampled too: rules `#5585bf`, the address/telefax/labels navy `#001f5f`, the web and e-mail addresses black and underlined. `request_form.css` holds these in px for the 714px sheet and `RequestFormPdf::Header()` in mm for the 190mm PDF — keep the two in step.
- **An answer is fitted to its printed line, never cut off and never pushed onto a new line.** A short blank gets smaller writing, down to ~5.5pt: `RequestFormPdf::row()` steps the size down until `NbLines()` fits the cell's `lines` (1 by default), and `request_form.js` (`fitRequestSheet()`, run by the viewer before measuring and by `request_form_view.php` on load) does the same in the browser. Only `rf-wrap` / `'wrap' => true` cells — the free-text notes — may wrap. This is what keeps **page 1 of the graduation form a fixed height**, so a long school name cannot push it onto a third page. **COLLEGE** is the one two-line blank (`'lines' => 2`, `.rf-2line`), double height as on the original, because its label leaves only ~32mm for the answer.
- The note and the course line stand **beside** the 2x2 photo box, as on the original, not above and below it.
- **Nothing of the blank form disappears when it is answered.** `rfField($label, $value)` prints the caption in black and always draws the rule beside it; the answer is written *on* that rule in ink blue (`--rf-pen`), so an unanswered field looks exactly like the printed original and a registrar can see at a glance what was filled in. The same holds in the PDF, where `row()` draws a line under every line the answer occupies. Keep this invariant when adding fields — never swap a rule out for text.
- The page counts are part of the fidelity: graduation is **2** pages, each letter **1**, as the printed originals are. Page 1 of graduation has ~1.7mm to spare (it ends at 283.3mm against FPDF's 285mm break) and, because every answer is fitted, that no longer depends on what the student typed. After adding rows or changing the letterhead, re-check `download_request_form.php`'s page count **with long answers** too, and that no HTML page grows past A4. When bumping `request_form.css` or `request_viewer.js`, bump their `?v=` in every page that links them.
- `request_form.css` styles it at a fixed A4 width in px, and normalises its own box model with a zero-specificity `:where()` reset so it looks identical inside the registrar page (which has a global CSS reset) and on the standalone page (which does not). It also carries the `@page` print rules. `.rf-page` is deliberately **not** `overflow: hidden` — the watermark is clipped by its own `.rf-watermark-layer` instead, so an over-long answer can never be silently cut off at the page edge.
- `request_form_view.php` serves it: `?id=N&mode=fragment` for the modal to `fetch()`, `?id=N` as a standalone page, `?id=N&mode=print` the same page with the print dialog opened. The standalone page scales the sheet down to the screen width on load and resize, and un-scales itself around `beforeprint`/`afterprint`. `download_request_form.php` rebuilds the same sheet as a real PDF with FPDF (core fonts are cp1252, so text goes through `$pdf->t()`; `row()` keeps a wrapping cell and its neighbours inside one set of borders and draws the rule under the answer; `pdfRegistrarStub()` and `requestPdfFileName()` are shared by both sheets). Both allow a registrar from the student's institution **or the owning student** — the student pages do not link them yet, but the check is there for direct URLs.
- **`request_viewer.js` + `request_viewer.css` are the one viewer**, used by both the registrar's **View** button and the student's **View my form**. Like `doc_viewer.js` it injects its own markup, so a page needs only the two stylesheets (plus `request_form.css` for the sheet), the script, and `openRequestForm({id, title, subtitle, status, theme, actions})`. It fetches the fragment and scales the whole sheet with a CSS transform, so text stays sharp at any zoom; the controls mirror `doc_viewer.js` — toolbar, `+`/`-`/`0`, Ctrl+wheel, pinch, double-tap, drag to pan — and the toolbar holds Print, Download PDF and open-in-a-tab.
  - Its colours are tokens on `.rv`: the defaults suit a light page and `theme: 'dark'` adds `.rv-dark` for the registrar's. The sheet inside is white paper on both.
  - `actions` are the caller's footer buttons — the registrar passes Approve / Reject / Reschedule / Mark claimed; the student passes none. Callers hand values over `data-*` attributes rather than interpolating them into inline JS.
- A closed request (rejected, claimed, cancelled) is watermarked across the sheet in both the HTML and the PDF, so a stale print-out is obvious.

### Notifications, email, audit
- `sendNotificationAndEmail($mysqli, $user_id, $message, $type, $subject)` in `notification_helper.php` is the single entry point for user-facing events. It inserts into `notifications` and sends an HTML email built by `buildEmailTemplate()` (`email_template.php`) through `sendEmail()` (`mailer.php`, PHPMailer over Gmail SMTP, logo embedded as `cid:logo_img`). Sending is synchronous, so broadcasts and event creation (`save_event.php` emails every student) send one SMTP message per recipient inside the request.
- `notifications.type` is an enum of `info`, `success`, and `warning`. `error` is not a valid value.
- The e-mail is built for Gmail: solid colours with `bgcolor` fallbacks (Gmail drops gradients, filters and `rgba()`), a light card, a phone media query, times in `Asia/Manila`, and a random Ref. in the footer so Gmail never folds repeated text behind "•••". The seal is `logo_email.png`, a correctly named copy of the combined seal `logo.jpg`, which is really a PNG, embedded as `image/png`. `sendEmail()` sets `CharSet = 'UTF-8'`. A broadcast passes `$variant = 'announcement'` through `sendNotificationAndEmail()` and gets a subject built from its opening words, so broadcasts don't thread together. Preview it with `email_preview.php?variant=announcement`.
- `logAudit($mysqli, $user_id, $action, $description, $target_user_id = null)` in `audit_log_helper.php` writes to `audit_logs` and never throws. IP addresses are intentionally not recorded or shown; older rows may still have a value in the unused `ip_address` column.
  - `$user_id` is whoever acted. It is `null` when nobody is signed in (`LOGIN_FAILED`, `LOGIN_BLOCKED`).
  - `$target_user_id` is the affected user, such as the student whose document or registration changed. Pass it whenever an action concerns a specific user, because the admin Audit Trail's program filter matches on the actor **or** the target.
  - Action names are UPPER_SNAKE (`LOGIN`, `DOCUMENT_APPROVED`, `STUDENT_ARCHIVED`, …). The dashboard picks each badge's color and icon from keywords in the name (`FAILED`/`REJECTED`/`DELETED` → red, `APPROVED`/`RESTORED` → green, and so on).
- **Audit Trail UI:** `admin_dashboard.php` loads rows from `fetch_audit_logs.php`, a systemadmin-only JSON endpoint. It does server-side filtering by program, action, search text and date range, pages 25 rows at a time, and returns per-action counts. `?format=csv` exports the filtered rows.
- `programs.php` (`getInstitutionPrograms()`) is the PHP list of courses per institution. It feeds the audit program filter and the dashboard's Institutions view. `index.php` still has its own JS copy for registration, so keep the two in sync.
- The OTP emails (`process_register.php`, `resend_otp.php`, `forgot_password.php`) build PHPMailer inline instead of calling `mailer.php`.

### Schema changes
There is no migration system. Schema changes happen at runtime in several places:
- `db.php` runs `ALTER TABLE notifications ...` and `ALTER TABLE documents ADD COLUMN reviewed_by / reviewed_at` on every request, wrapped in try/catch. This relies on PHP 8.1+ mysqli throwing exceptions.
- `audit_log_helper.php` creates `audit_logs` if it's missing.
- `admin_dashboard.php` creates `courses` if it's missing.
- `process_register.php` adds `users.section` if it's missing.
- One-off scripts (`migrate_profile.php`, `patch_db*.php`, `add_archived.php`) were run manually.

New columns follow the same idempotent "check then ALTER" pattern. The `events` table has both `start`/`end` (used by the code) and legacy `start_date`/`end_date`. The `submissions`, `requests`, and `enrollments` tables exist in the DB but no code uses them (the request feature has its own `student_requests` table; the 5-column `requests` table is still dead). The `submissions.php` page reads from `documents`.

### Backup/restore
`backup_db.php` and `restore_db.php` (systemadmin only) shell out to `C:\xampp\mysql\bin\mysqldump.exe` / `mysql.exe`, falling back to `PATH`.
